# 描述文档建立技能

风格参考：[视频播放页.md](../classify_shower/功能添加记录/视频播放页.md) 的“保存某视频剧集上一次观看到的位置”一节。用于编写本项目的功能添加记录；用户指定章节时，沿用该章节的标题层级和范围。

## 描述风格

以连续的中文自然段描述功能。先点出关键命令或字段及其含义，再说明它从哪里取得、如何处理、交给谁使用，最后说明需要保存或更新的数据。使用“该值通过……”“然后前端……”“这个方法还要……”等衔接，让后一个动作承接前一个动作的结果。

命令、键名、函数名和路径使用行内代码，保留代码中的准确拼写。路径先说明相对哪个目录，再给出具体例子，例如 `<完整视频文件名（含扩展名）>@meta/` 对应 `xxx.mp4@meta/`，不要只写“读取配置文件”。字段与含义放在一起说明，例如“读取 `video-time` 键值作为 `auto-seek-time` 键值，若读取失败设为0”。默认值和失败行为必须有代码依据。

数据结构不容易用一句话说清时，插入一个小的 JSON 示例，并在相邻正文解释关键字段。时间变换用具体输入和输出说明执行顺序、边界和单位。示例使用合法 JSON；说明文字放在代码块外。

正文优先解释功能行为和数据之间的联系，不逐行翻译代码，不堆叠函数清单、行号表或开发过程。只有外部接口约定直接影响理解且已核实原文时，才像参考段落一样引用接口说明；不要根据记忆编造引文。

## 根据代码补全文档

先阅读目标段落及相邻章节，再沿入口、核心处理函数、必要的调用方和结果使用处核对数据流。重点确认请求与响应、文件位置和格式、处理顺序、默认值、失败回退及写入副作用。只追踪足以解释本次功能的代码。

按“触发或响应字段 → 读取位置和示例 → 数据处理 → 前端使用 → 保存结果”的顺序组织内容；根据真实流程调整顺序，省略不适用的部分，不为凑结构增加无关章节。补写现有小节时直接加入正文。

描述现有实现时用“读取”“返回”“写入”等确定表述；尚未实现的需求才用“要”“应该”。参数名、注释和局部变量不能单独证明功能已生效，需要确认调用时是否传递、结果是否实际使用。如果设计意图与实现不同，用一段短说明区分两者，不把预期行为写成现状，也不顺带修改代码。

完成后逐项核对示例、边界条件和字段去向，确认只修改用户要求的文档范围。用实际任务检验此技能：读者应能沿正文还原数据从读取到使用或保存的过程，而不必再根据函数清单自行拼接流程。
