# 弹幕资源批量更新工具

***

## srcURL-downloader-CM.py

可以同时下载并构建弹幕数据的和评论数据的批量下载器。

`basepath.json` 中应填写视频对应的元数据目录路径，命名为 `<完整视频文件名（含扩展名）>@meta/`。以下以视频 `xxx.mp4` 及其同级目录 `xxx.mp4@meta/` 为例。

对于`./basepath.json`文件里的每一个需要更新弹幕的文件夹，在下载构建完成弹幕数据后，默认根据元数据文件夹`xxx.mp4@meta`下的`dm-srcURL.json`文件来构建 `xxx.mp4@meta/cm-srcURL.json` 文件，并据此下载构建评论数据文件。classify\_shower 采用sqlite数据库存储评论数据，数据库文件结构版本v1.1。有关该结构的详细说明，请参考 [数据库结构](评论下载工具.md#评论数据库v11结构)。

### 构建步骤描述

根据 `dm-srcURL.json` 中的每一条BV号，以如下格式构建 `xxx.mp4@meta/cm-srcURL.json` 文件：

```json

[
    {
        "src":"B站",
        "BV": "BVXXXXXX",
        "name":"来源1"
    },
    {
        "src":"B站",
        "BV": "BVXXXXXX",
        "name":"来源2"
    },
    ......
]

```

若 `xxx.mp4@meta/cm-srcURL.json` 文件存在，则读取文件内容，将新的内容合并后写回。

然后检测是否存在(如不存在则创建) `xxx.mp4@meta/` 文件夹同级文件夹 `__COMMENT__/` 文件夹，检测是否存在(如不存在则创建) `__COMMENT__/cm-list.json` 文件。

读取 `__COMMENT__/cm-list.json` 文件内容，这个文件内容示例如下：

```json
{
    "BVXXXXXX":{
        "file-name":"cm1.db",
        "aid":1234567891011,
        "update-time":1234567890,
        "comment-count":1000,
        "reply-count":200,
        "src-name":"动漫铥铥",
    },
    "BVXXXXXX":{
        "file-name":"cm2.db",
        "aid":1234567891012,
        "update-time":1234567990,
        "comment-count":500,
        "reply-count":100,
        "src-name":"MCE汉化组"
    },
    ......
}
```

然后根据 `xxx.mp4@meta/cm-srcURL.json` 内容，对其中每一条BV号作为键，在 `__COMMENT__/cm-list.json` 中查找对应字典。

如果存在该BV号对应的字典，则更新 `aid` 和 `update-time` 字段并写回 `__COMMENT__/cm-list.json` 文件。创建文件路径(如需要)并尝试下载合成评论数据库到 `__COMMENT__/raw/<file-name>`，如果文件存在则直接覆盖。`__COMMENT__/update/` 文件夹用于存储`__COMMENT__/cm-list.json` 文件中每个来源评论的数据库文件以及之后更新评论产生的增量数据库文件，其涉及到的文件结构为：

```
......
├── __COMMENT__/
│   ├── update/        
│   │   ├── cm1.db     (来源1第1次获取到的原始评论数据)
│   │   ├── cm1-2.db   (来源1第2次获取到的原始评论数据在cm1.db上的增量数据库文件)
│   │   ......
│   │   ├── cm1-x.db   (来源1第x次获取到的原始数据在来源1合并库上的增量数据库文件)
│   │   ├── cm2.db     (来源2第1次获取到的原始评论数据)
│   │   ├── cm2-2.db   (来源2第2次获取到的原始评论数据在cm2.db上的增量数据库文件)
│   │   ......
│   │   └── cmy-x.db   (来源y第x次获取到的原始数据在来源y合并库上的增量数据库文件)
│   ├── cm1.db     (update 文件夹里来源1的数据库和所有增量库的合并数据库文件)
│   ├── cm2.db     (update 文件夹里来源2的数据库和所有增量库的合并数据库文件)
│   ├── cm3.db     (update 文件夹里来源3的数据库和所有增量库的合并数据库文件)
│   ......
│   ├── cmy.db     (update 文件夹里来源y的数据库和所有增量库的合并数据库文件)
│   ......
```

假设 `<file-name>` 为 `cm<number>.db`（例如 `cm1.db`），程序先调用 `rebuild_merged_database`，以 `__COMMENT__/update/cm<number>.db` 为基库，按增量文件名中编号的数值升序重放本来源的全部增量数据库，输出为同目录的临时库(即是执行了合并操作)，校验后再替换 `__COMMENT__/cm<number>.db`；新增评论直接加入，变化评论按同一 `rpid` 用后处理的完整记录覆盖，历史缺失评论保留。同时将各增量的删除记录合并到 `__COMMENT__/update/cm<number>.deletelist`。具体规则见下文 [合并评论基库与全部增量数据库](评论下载工具.md#合并评论基库与全部增量数据库)。

在获取到 `__COMMENT__/cm<number>.db` 文件后，将其与 `__COMMENT__/raw/<file-name>` 文件进行对比，创建新的增量数据库到 `__COMMENT__/update/` 文件夹里，获取文件夹中所有类似这样 `cm<number>-1.db`、`cm<number>-2.db` ...... 的库，然后找到一个最大的 n ，使得`cm<number>-n.db` 在该文件夹里存在，新增量数据库的名称将是 `cm<number>-<n+1>.db`。然后将新的增量数据库文件与`__COMMENT__/cm<number>.db` 文件进行合并，更改执行到 `__COMMENT__/cm<number>.db` 文件中。同样在执行合并操作的同时读取新的增量数据库里 被删掉的评论数据 的rpid，将其合并(或创建)到 `__COMMENT__/update/cm<number>.deletelist` 文件里。然后删除 `__COMMENT__/raw/<file-name>` 文件。然后根据最后 `__COMMENT__/cm<number>.db` 文件里 `main` 表和 `reply` 表的长度来更新 `__COMMENT__/cm-list.json` 文件里对应来源字典的 `"comment-count"` 键值和 `"reply-count"` 键值。如果 `__COMMENT__/cm-list.json` 里 `src-name` 字段缺失，则根据 `xxx.mp4@meta/cm-srcURL.json` 中的 `name` 字段获取后补上。

在这之后，检测是否存在(如不存在则创建) `__COMMENT__/resources-URL.json`, 然后读取 `resources-URL.json` 并将新资源URL与之合并后写回，并按需下载新资源到 `__COMMENT__/comment-resource/`, 然后检测`__COMMENT__/bilibili-resource` 里文件列表是否完整，若需要则解压 `工具链\评论下载工具\bilibili-resource.zip` 到 `__COMMENT__/bilibili-resource`。 评论数据库和资源具体的下载方法参考 `工具链\评论下载工具\bili-comment-downloader(DB).py`，复制其中的函数并根据需要略微修改，大同小异。

如果不存在该BV号对应的字典，则创建一个新字典，包含 `file-name`、`aid`、`update-time`、`comment-count`、 `reply-count`字段。`file-name`循环尝试 `cm1.db`、`cm2.db`、`cm3.db` 等，直到找到一个不存在的文件名。然后将 `aid` 设置为该BV号对应的AV号(`bilibili_api.utils.aid_bvid_transformer.bvid2aid` 方法)，`update-time` 设置为当前时间戳。写回更新 `__COMMENT__/cm-list.json`。然后创建文件路径(如需要)并下载合成评论数据库到 `__COMMENT__/update/<file-name>`，复制一份到 `__COMMENT__/<file-name>`，并根据这个文件里 `main` 表和 `top` 表(置顶评论和主评论表长度之和)、`reply` 表的长度来更新 `__COMMENT__/cm-list.json` 文件里对应来源字典的 `"comment-count"` 键值和 `"reply-count"` 键值。检测是否存在(如不存在则创建) `__COMMENT__/resources-URL.json`, 然后读取 `resources-URL.json` 并将新资源URL与之合并后写回，并按需下载新资源到 `__COMMENT__/comment-resource/`, 然后检测`__COMMENT__/bilibili-resource` 里文件列表是否完整，若需要则解压 `工具链\评论下载工具\bilibili-resource.zip` 到 `__COMMENT__/bilibili-resource`。 `__COMMENT__/cm-list.json` 里 `src-name` 字段则根据 `xxx.mp4@meta/cm-srcURL.json` 中的 `name` 字段获取。

最后，检测是否存在(如不存在则创建) `xxx.mp4@meta/cmif.json` 文件。读取 `xxx.mp4@meta/cmif.json` 文件内容，这个文件内容示例如下：

```json
[
    {
        "comment-srcfile":"cm1.db",
        "resource-folder":"",
        "basic-resfolder":"bilibili-resource",
        "src":"B站"
    },
    {
        "comment-srcfile":"cm2.db",
        "resource-folder":"",
        "basic-resfolder":"bilibili-resource",
        "src":"B站"
    },
    ......
]
```

查找其中有没有 `comment-srcfile` 为 `cm<number>.db` 的字典。若有则不改动，若没有则创建一个新字典，包含 `comment-srcfile`、`resource-folder`、`basic-resfolder`、`src` 字段。`resource-folder`、`basic-resfolder`、`src` 字段恒定与示例里面的一样，然后`comment-srcfile` 字段填 `cm<number>.db`。写回 `xxx.mp4@meta/cmif.json` 文件。这样完成了整个构建步骤。

### 合并评论基库与全部增量数据库

`__COMMENT__/cm<number>.db` 用于保存一个评论来源历次抓取后保留下来的评论数据，供后续生成增量及读取评论使用。这里的 `__COMMENT__/` 位于视频元数据目录的同级，例如与 `xxx.mp4@meta/` 同级。`update/cm<number>.db` 保存基库，`update/cm<number>-<n>.db` 保存第 `n` 个编号的增量，最终合并库位于 `__COMMENT__/` 根目录。合并库中的主评论（`main` 表）、置顶评论（`top` 表）、子评论（`reply` 表）通过 `member`、`content` 引用对应的用户和内容记录。

其中增量库保存新增或变化评论的完整记录及其对应实体，并不只保存变化字段。生成增量的 `create_comment_delta` 比较评论的九字段哈希（`_volatile_hash`），以及用户、内容的引用和数据哈希（`_data_hash`），决定哪些记录需要保存；合并阶段直接应用这些记录，不再次逐条比较哈希，也不依靠 `_changes` 表逐字段打补丁。

每个来源还有一个历史删除清单 `__COMMENT__/update/cm<number>.deletelist`，保存所有历史增量中曾经缺失的评论或回复 `rpid`，示例如下：

```json
[10001, 10002, 10005]
```

其中每个数字是一个 `rpid`，按数值升序保存且不重复。它是各增量 `_deleted_records` 表的并集，不代表当前仍然缺失的评论集合；某条评论在后续重新出现，也不会从这份历史清单中移除。这份清单不参与删除合并库中的评论。

#### 读取顺序与单个增量的处理

处理已有来源时，`process_comment_sources` 在抓取本次评论之前调用 `rebuild_merged_database(update_dir, file_name, merged_path)`。它先确认基库存在；如果基库缺失但根目录已有合并库，则将现有合并库复制到基库位置作为检查点，如果两者都不存在则报错。随后 `delta_paths` 从 `update/` 中选择本来源符合 `cm<number>-<正整数>.db` 命名的文件，按后缀整数升序排序，因此 `cm1-2.db` 排在 `cm1-10.db` 之前，与目录枚举顺序无关。

重建时先把基库复制到 `__COMMENT__/cm<number>.db.rebuild.tmp`，所有历史增量都作用于这个临时库。程序复用一个 SQLite 连接，将临时库的页缓存设置为约 64 MiB，临时表放在内存中，并关闭临时库的回滚日志、中间同步和逐语句外键检查；这些设置仅用于可丢弃的重建临时库。存在增量时，旧版基库缺少的 `top` 表会先补齐。

对每一个增量，程序将它附加为 `delta_db`，校验增量版本和九字段哈希口径，然后调用 `_apply_attached_comment_delta`。该函数先为目标表补上增量中新出现的列，再将这个增量的 `main`、`top`、`reply` 表中所有 `rpid` 去重写入临时表 `_apply_ids`；旧版增量没有 `top` 表时，只读取 `main`、`reply`。

对于 `_apply_ids` 中的每一个 `rpid`，目标库先删除三张评论表中的同号记录，再删除 `member`、`content` 中 `parent` 等于该 `rpid` 的记录，然后从增量批量插入新的实体及评论。因此处理单位是同一 `rpid` 的整组记录，评论从主评论转为置顶等分类变化也随之生效；后一个增量没有某条评论时，之前保存的版本继续保留。若后一个版本不再含某个实体或旧字段，原实体会被移除，未提供的列按目标表默认值写入（动态添加的列通常为 `NULL`）。

处理这个增量时还会读取 `_deleted_records` 表，将其中的 `rpid` 加入内存删除集合，不需要重开增量文件。随后提交当前增量事务并解除附加，再处理下一个增量。因此当前实现仍是逐增量重放、逐增量提交；优化主要来自复用连接、减少临时库日志写入、避免反复全库检查，以及在同一次读取中收集删除记录，并不是先把全部增量读入内存后只写入一次。

#### 最终统计与输出

所有增量处理完后，`_finish_comment_merge` 统一统计 `main`、`top`、`reply` 数量，将结果分别写入 `_metadata` 的 `main_count`、`top_count`、`reply_count`，并更新合并库来源标记及生成时间，最后执行一次外键检查和一次完整性检查。没有增量时保留基库原有结构、元数据，只进行最终校验。

校验通过后关闭连接，调用 `os.fsync` 同步临时库，再通过 `os.replace` 替换根目录合并库。随后将内存中的删除集合排序，经 `write_comment_deletelist` 写入 `.deletelist`。这两个文件分别替换，不构成跨文件原子事务；数据库替换前失败会保留原合并库并清理临时库，如果删除清单写入失败，则可能出现合并库已更新、删除清单尚未更新的情况。

本次抓取完成后，`next_delta_path` 只枚举一次 `update/`，从本来源已有增量文件中取最大后缀 `n`，返回 `cm<number>-<n+1>.db`；没有增量时返回 `cm<number>-1.db`。例如已有 `cm1-1.db`、`cm1-4.db` 时，下一份为 `cm1-5.db`，不会补用 `cm1-2.db`。生成新增量后，调用方将其应用到当前合并库、合并删除清单，并用 `main + top` 的数量更新 `cm-list.json` 的 `comment-count`，用 `reply` 的数量更新 `reply-count`。

#### 文件编号与实际生成顺序不一致时

当前合并算法以文件名后缀代表版本顺序，不使用文件系统创建时间、修改时间，也不使用增量库 `_delta_metadata.created_at_utc` 来判断先后。因此目录枚举顺序打乱不影响结果，但文件编号与实际生成顺序打乱时，不能保证保留真实的最新版本。

例如同一条评论按真实生成顺序分别保存为 `cm1-4.db`、`cm1-2.db`、`cm1-1.db`、`cm1-3.db`，四份记录中的 `like` 分别为 10、20、30、40。重建实际按 `cm1-1.db` → `cm1-2.db` → `cm1-3.db` → `cm1-4.db` 处理，`like` 依次变成 30、20、40、10，最终保留第一次生成的旧版本 10，而不是最新值 40。评论所属分类及用户、内容记录也受相同覆盖顺序影响。

如果各增量涉及的 `rpid` 完全不重叠，或重复记录内容完全相同，单纯打乱顺序可能不改变结果；历史删除清单本身只是集合并集，也不受顺序影响。但是只要存在同一 `rpid` 的不同版本，通常就必须按真实版本顺序重放。此次改为最大编号加一，可以避免以后因补空号造成顺序倒退，但不会自动修复已有错序历史。对于已经错序的文件，需要先确认真实生成顺序，再安全调整编号；若要改为按时间排序，应另行定义时间缺失、相同时间及时间不可信时的处理规则，当前尚未实现。

### 评论数据库v1.1结构
