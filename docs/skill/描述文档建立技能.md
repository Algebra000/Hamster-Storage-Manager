# 描述文档建立技能

风格参考：[视频播放页.md](../classify_shower/功能添加记录/视频播放页.md) 的“保存某视频剧集上一次观看到的位置”和用户修订的“生成 `dm-info.json` 并发送”两节。前者参考数据读取与前后端衔接，后者优先参考文件用途、结构示例和生成逻辑的组织方式。用于编写本项目的功能添加记录；用户指定章节时，沿用该章节的标题层级和范围。

## 描述风格

围绕当前小节的对象展开叙述。描述一个文件或响应数据时，先用一句话说明它保存什么、用于什么，再展示结构、解释字段，随后说明这些数据如何生成和使用。让读者先认识处理的对象，再理解操作过程，不必从代码执行的第一步开始写。按“读取”“生成并发送”等职责分节，避免一个小节承载整条功能链路。

以连续的中文自然段展开，每段说明一个层次。使用“其中……”“这些信息是在……得到的”“关于子函数……”“所有的……执行完后”“最后……”衔接上下文。可以为不同参数或明确的操作步骤使用列表，不把自然段作为唯一格式，也不机械套用连接词。

命令、键名、函数名和路径使用行内代码，保留代码中的准确拼写。路径先说明相对哪个目录，再给出具体例子，例如 `<完整视频文件名（含扩展名）>@meta/` 对应 `xxx.mp4@meta/`，不要只写“读取配置文件”。字段与含义放在一起说明，例如“读取 `video-time` 键值作为 `auto-seek-time` 键值，若读取失败设为0”。默认值和失败行为必须有代码依据。

当小节以生成或读取某个 JSON 文件为主题时，优先在用途说明后给出完整而精简的结构示例，保留理解所需的顶层字段和嵌套层级。多个列表项能说明同名项、分组或合并关系时可以保留，不为缩短示例而丢掉这些关系。示例后先解释主要字段承载什么，再讲数据从哪里来。示例使用合法 JSON，说明文字放在代码块外；数量、汇总值等应相互一致，学习参考文的写法时仍要独立核对示例数值。时间变换用具体输入和输出说明执行顺序、边界和单位。

字段解释优先采用“业务含义（`键名`键）”，例如“来源名称（`name`键）、更新时间（`update-time`键）”，不要只罗列英文键名。嵌套结构中同名键需要说明所属对象，例如每个来源的 `dm-count` 与整个文件的 `dm-count` 分别统计什么。

正文优先解释功能行为和数据之间的联系，不逐行翻译代码，不堆叠函数清单、行号表或开发过程。关键函数应放在它负责的动作中介绍，写清所属方法、调用时机、输入对象和输出用途；若其内部规则影响理解，再用“关于子函数……”另起一段展开。例如先说明 `make_danmaku_data` 的子函数 `get_source_info` 从单次重映射后的弹幕列表统计来源，再说明按 `src` 分组、计数和取最大 `send-time` 的规则。

说明统计或合并逻辑时，明确每次处理的单位、分组依据和最后汇总的范围。例如“单个弹幕文件经某项配置处理后的列表”“该列表中同一 `src` 的弹幕”“各项处理所得来源列表的简单合并”是不同层次，不能都简称为“来源”。优先用具体操作解释结果，例如“各列表直接追加到 `dm-src`”能说明为何其中可能有同名项；额外限制只在有助于理解时补充。

只有外部接口约定直接影响理解且已核实原文时，才像参考段落一样引用接口说明；不要根据记忆编造引文。

## 根据代码补全文档

先阅读目标段落及相邻章节，再沿入口、核心处理函数、必要的调用方和结果使用处核对数据流。重点确认请求与响应、文件位置和格式、处理顺序、默认值、失败回退及写入副作用。只追踪足以解释本次功能的代码。

生成文件类小节优先按“文件用途 → 结构示例 → 字段含义及数据来源 → 关键函数内部规则 → 全部结果汇总与写入 → 返回和前端使用”组织。请求或读取类小节则可从触发命令开始。按读者理解所需的顺序介绍概念，在叙述实际执行先后时仍以代码为准；省略不适用的环节，不为凑结构增加无关章节。

描述现有实现时用“读取”“返回”“写入”等确定表述；尚未实现的需求才用“要”“应该”。参数名、注释和局部变量不能单独证明功能已生效，需要确认调用时是否传递、结果是否实际使用。如果设计意图与实现不同，用一段短说明区分两者，不把预期行为写成现状，也不顺带修改代码。

完成后检查：读者是否先知道数据的用途和结构，能否区分单项处理与整体汇总，是否知道关键函数处理哪个对象、结果填入哪个字段，以及哪些数据落盘、哪些只用于返回。逐项核对示例、边界条件和字段去向，确认只修改用户要求的文档范围。
